## Blockers

### B1 — P1: stale closure decisions survive a failed accounting revision check

Locations: `api/crates/cma/src/store/budget/spend_ledger.rs:97`, `api/crates/cma/src/store/budget/period.rs:296`.

`evaluate_period` reads a period and computes its transitions. If a concurrent settlement, release or observation correction changes the period, its revision-CAS update can match no document. The code clears only `evaluation.lifted` and still calls `enter_closures` with the old `evaluation.entered`. That update filters only the period key and absence of the same closure reason. It does not fence the row revision, current settings revision or current accounting evidence. The refused-admission path uses the same unfenced insertion helper.

Therefore a decision derived before a concurrent correction can install a fleet-wide STOP after the correction has removed its justification. The strongest interleaving is an old evaluation completing after a newer policy and evaluator have already lifted STOP: the old closure is reintroduced despite that completed lift. This is not merely delayed telemetry: admission consumes the closure, running turns receive durable stops, and the pause sweep acts on it. The pure state machine deliberately requires a newer settings revision to lift a spend closure, so re-evaluating under the unchanged revision does not repair this wrong STOP. Old evaluator work can also race a deliberate lift.

Reproduction: `2026-11-12-pr1741-sec/reproduce-stale-closure.js` executes the exact Mongo update predicates against a disposable local Mongo. It confirms that a newer settings revision/lift is persisted, the old revision CAS misses, and the following stale STOP insertion succeeds; a control with a revision-fenced insertion refuses it. This reproduces the database interleaving, not an invocation of the entire Rust evaluator.

Required: discard/recompute all transitions after a CAS miss and make entry/lift persistence atomic with the exact ledger and policy evidence. Apply the same protection to refusal-generated closures. Cover concurrent correction, release, settings change and closure lift.

### B2 — P1: cached STOP is authority to cancel newly admitted work after a lift

Locations: `api/crates/cma/src/store/budget/source.rs:60`, `:86`, `:139`, `:169`; related pause authority: `api/crates/cma/src/sandbox/reconciliation_platform.rs:54`, `api/crates/cma/src/store/sandbox_maintenance/transaction.rs:112`.

The five-second stop cache is keyed only by the period string. `current_stop` reads current settings but passes only the policy into `platform_stopped`; the settings revision is unavailable to the cache. Once the evaluator lifts STOP under a newer revision, ordinary admission can accept a new turn while a cached positive STOP still exists. `stop_requested` then persists `PlatformExhausted` under that new turn's immutable stop key. Waiting out the cache does not remove that durable cancellation.

The pause lane has the same authority problem: its fifteen-second cached positive answer can create new `PlatformSpendStop` pause requests after a lift. The maintenance transaction rechecks busy-work and resource fences, but never rechecks the spend closure/settings; this cause also bypasses keep-alive policy. On evaluation errors the previous positive answer can continue being used beyond the cache interval.

An added reviewer-only Rust/Mongo probe reproduced this end to end: warm positive cache, complete old turn, advance settings and lift closure, admit/start a different turn, then receive a durable platform stop for that different turn.

Required: treat cached positive answers as hints; bind any new durable stop/pause to current authoritative closure/policy evidence. Cover lift followed immediately by new admission, an ordinary live turn, and keep-alive/agentless Sandbox pause. Retain already-valid stop receipts without applying them to later turns.

### B3 — P1: revival and registration fail open on missing or stale metering evidence

Locations: `api/crates/cma/src/store/budget/spend_ledger.rs:110`; consumers `api/crates/cma/src/auth/records.rs:83`, `api/crates/layer2-core/src/sandbox/control/service.rs:68`, `api/crates/layer2-core/src/sandbox/lifecycle_service.rs:185`.

`admission_state` ignores its `now` argument, reads only persisted closures, and maps an absent period row to an empty closure list even when metering is configured. A missing observation, expired observation or ended period also appears open until another path persists `MeteringUnavailable`. Revival and first-time registration consume this answer as authority. This admits new commitments during initial activation, between expiration and evaluation, or indefinitely if the evaluator cannot persist its result, despite #1496's fail-closed rule. Transactional command admission already derives missing/stale evidence directly and refuses, so the entry points disagree.

An added reviewer-only Rust/Mongo probe configured the meter with no period row: `admission_state` allowed both commitment and registration while command reservation against the same state correctly refused as unavailable.

Required: derive fail-closed admission from the current policy, time and period evidence at each authoritative decision, independently of the evaluator having written a closure. Keep the explicitly permitted existing-owner sign-in behavior. Test missing period, absent observation, expired source, finished period and evaluator unavailability.

### B4 — P1: enabled platform metering permits unreserved requests for unbudgeted owners

Locations: `api/crates/cma/src/store/budget/requests/admission.rs:34`, `api/crates/cma/src/store/budget/mod.rs:151`; regression demonstrating the behavior: `api/crates/cma/src/store/sandbox_mongo_integration_tests/command_ledger_tests/platform_unbudgeted_tests.rs:123`.

With the platform cloud meter enabled, an owner without a default or explicit owner policy takes the `Ok(None)` path after a zero-liability open check. It bypasses model/rate lookup and quoting. The new test deliberately passes an unconfigured model and expects no hold. The existing production request adapter maps this to no permit, and the title/suggestion sender still issues the upstream request (`sandbox/model_request_budget.rs:33`, `sandbox/titles.rs:164`). Command/turn admission likewise creates no liability for such owners. Those requests never contribute reservations or settlements to the platform row.

This conflicts with the [accepted #1496 pre-request reservation contract](https://github.com/ChronoAIProject/cma/issues/1496#issuecomment-6774696408): every initiated/brokered model request needs a conservative owner/operation-bound hold, and an unknown valuation refuses. The pre-existing opt-in owner-budget behavior does not provide a platform-wide cap once this PR enables the global meter. The author's new decision/test does not establish an approved exception to the accepted contract.

Required: when global metering is enabled, refuse missing owner/model valuation or provide a trusted policy that reserves every request. Preserve the historical bypass only while global metering is disabled. Test the actual provider boundary to prove no send occurs without the required hold.

### B5 — P1: failed platform pause can automatically reopen under STOP

Locations: changed orchestration `api/crates/cma/src/sandbox/reconciliation_schedule.rs:9`; downstream `reconciliation_recovery.rs:109`; `api/crates/layer2-core/src/sandbox/runtime_update_service.rs:103`, `unpublished_recovery.rs:218`, `unpublished_recovery_transition.rs:30`, `lifecycle_execution.rs:484`.

The new STOP check defers the ordinary runtime-update phase, but `run_due` discards that check's result and continues the separate automatic failed-runtime recovery lane. A retained-home platform pause that fails before runtime suspension can become Failed/`restore_failed` with its runtime binding intact. Failure clears the original pause intent and retained pause notice. It then satisfies unpublished-recovery eligibility; `recover_failed_unpublished` reads no platform spend authority, starts a replacement/rotation, and can return it to Active because the original pause intent is gone. A later sweep pausing it again does not prevent the new runtime commitment or the interval of reopened service.

The branch's `docs/plans/platform-spend/NOTES.md:359` also explicitly records this as an unfixed, untested follow-up. It affects the new STOP behavior, even though parts of the recovery mechanism predate this PR.

Required: preserve the platform pause intent through failure and/or refuse automatic reopening while authoritative STOP is active. Cover failure before suspension, recovery discovery/admission, lift and retry; allow safe pause-completion work without reopening service or replaying runtime input.

## Authorization, scope and confidentiality

- The only new mounted routes are `GET /api/v1/admin/spend` and `POST /api/v1/admin/spend/observations`. Both use `AuthenticatedCaller` and require `ConfigurePlatform` in the core service. POST also requires it before body validation. `ReadAllSandboxes` alone is insufficient. Existing binding-token restrictions remain in the shared authentication middleware.
- Cloud observations use strict request fields and a fixed source enum, validate timestamps and bounded integer input, and derive the current platform period server-side. No caller-provided tenant key chooses an accounting record.
- Existing platform settings retain `ConfigurePlatform` authorization and expected-revision replacement. The new cloud fields are guarded by both the existing budget writer gate and the new spend writer gate. Owner revival retains owner checks; command revival retains resource authorization; no new route was found that gives an ordinary caller global stop or observation authority.
- Reservations derive owner identity from the stored Agent and retain exact Agent/turn/request bindings. Settlement checks the original hold; proven non-dispatch is required for release. Unknown request commit outcomes refuse a new send permit. The identified gaps concern missing coverage and stale authority, not a new direct cross-tenant selector.
- Financial data is returned only by the privileged spend/settings surfaces in this delta. Public HTTP failures and shared terminal projections use fixed codes/guidance. Closure logs carry reason and settings revision, and the observation audit carries revision; neither emits spend figures. No public UI displaying the figures is added. SDK changes add admin settings types only.
- Nonblocking audit follow-up: observation persistence and its activity audit are separate writes. An audit/readback failure can return unavailable after the observation committed; an identical retry is accounting-idempotent but may duplicate audit records. No atomic audit guarantee is claimed by this review.

The existing model-budget and model-request writer flags remain default false. There are no additional environment flags in the delta. Cache TTL, evaluation interval and refresh interval are fixed code constants, not operator config keys.

The new flag gates writes of the new configuration/observation shapes; closing it does not disable a persisted active meter. Removing `cloud` or disabling budgets disables the live meter, while retained obligations must still settle. It is not a universal runtime kill switch.

No new collection, index, validator or TTL is added. Existing `model_budget_reservations` gains `platform:<period-start>` and immutable `observation:cloud:<period-start>:<observed-through>` records. Turn/request records gain optional `period_start`; stop/failure representations gain the platform-exhausted variant. Point operations use `_id`; period replacements also compare the revision.

There is no backfill. Existing reservations with no `period_start` never mirror into the new row. Activation therefore requires an explicit baseline/accounting plan for pre-existing obligations; a lazy empty period must not be mistaken for a historical usage census. This review does not approve production activation or private accounting inputs.

After new fields/records are written, old strict readers are not a safe rollback floor. Removing the cloud configuration does not erase retained fields. The documented prerequisite is the retirement-census extension #1754 merged and deployed before activation; #1754 remained open at this review's check. An OFF deployment may be assessed separately after code blockers are fixed, but activation is not ready.

## Incremental Mongo load

Counts below are logical collection operations, excluding transaction protocol commands, retries, and unchanged owner/command/Agent work. They describe the enabled steady state unless stated otherwise.

| Path | Added operations from the platform layer |
| --- | --- |
| Budgeted command reservation / direct turn reservation | One period read plus one period replacement; initial row may add an insert. Existing settings fence/read remains. |
| Already-reserved queued turn starts | An additional settings read and period read for the current open check; liability transfers without a second period charge. |
| Auxiliary model-request reserve | One period read and replacement, in addition to existing owner/request accounting. |
| Request settlement, terminal turn settlement, proven non-dispatch release | One charged-period read and replacement. |
| Usage exceeds retained liability | One period read and replacement. Ordinary usage frames do not all add a period write; existing owner/turn writes remain. |
| New Sandbox / Workspace / Agent / Launch | One settings read even when metering is OFF; one additional period read when enabled. Open zero-liability checks do not write the period/settings fence. |
| Unbudgeted command / turn / auxiliary request | An extra settings read for `require_open`, even when OFF, and a period read when enabled. No global liability hold: B4. |
| Revival and admission-state read | One settings read, plus one period read when enabled. No write; B3 concerns evidence validity. |
| OAuth callback | Added user-directory read; existing owners short-circuit. New owners additionally read settings and, when enabled, the period. Registration entry/options also read admission state. |
| Running-turn STOP poll | One period read on cache miss, none on hit; current Agent, stop-key and settings reads predate this delta. Concurrent misses are not single-flight, so the TTL is not a strict one-query-per-interval bound. |
| Evaluator, each replica, nominal fifteen-second interval | Enabled: four reads across `evaluate_period` and `admission_state`, plus an unconditional `$setOnInsert` upsert attempt. Changes/sixty-second refresh add a period CAS update; entered closures add guarded updates. OFF: one settings read per evaluation. |
| Observation POST | Settings/observation/period reads, immutable observation insert and period replacement in one transaction, followed by readback and a separate audit write. |

OFF is not a zero-overhead deployment: the new create/revival/registration checks and evaluator still read settings, and a cold process initially takes the writer mutex until it learns metering is disabled. This adds a settings-store availability dependency on those paths.

Every enabled reservation/settlement contends on the same period row across replicas. The process-local mutex queues liability writers for the entire transaction retry loop, coupling different tenants' latency, while Mongo remains the cross-replica authority. This needs a representative concurrency/checkout-hold benchmark before activation; passing functional tests does not establish production capacity.

The STOP sweep reuses global paginated maintenance discovery and full per-Sandbox Agent/Workspace proofs, and now runs even when ordinary auto-pause is disabled. Legacy proofs can scan retained Agent logs; Workspace proof reads the complete Sandbox set and fences each row. These are not new per-turn fleet scans, but STOP can activate substantial existing scan/write work at the same time as global admission contention. No production performance measurement was made in this read-only review.
