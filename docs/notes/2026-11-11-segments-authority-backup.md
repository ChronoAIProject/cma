# Segmentation runtime authority and coherent recovery inventory

Part of #1348–#1351; pre-review P1-2. This record describes source configuration and release qualification. It grants no production authority and authorizes no migration, role change, backup restoration or activation.

The runtime inventory must include the original `agents` and `agent_log` collections, plus all nine additive sidecars: `agent_log_heads`, `agent_log_segments`, `agent_log_publications`, `agent_log_projections`, `agent_log_evidence`, `agent_log_audits`, `agent_log_gates`, `agent_log_admissions`, and `agent_capacity_recovery_work`. The last collection accepts only outer BSON Int64 format_version 2 with its original result witness. A v1 draft is never registered, relabeled or used as authority.

The exact runtime role continues the existing Agent Manager collection/action contract; no database wildcard, foreign-service collection, dropCollection or new dropIndex privilege is added. The runtime role generator prints desired grants and validates configured credentials; it does not provision a role. Release-owner provisioning/readback is a separate explicit infrastructure action. Migration and audit/gate operator roles remain separate; migration uses only its reviewed additive DDL and ledger lease, and no service startup performs DDL or chooses a cohort.

A usable backup/restore unit is the consistent database snapshot containing original Agent envelopes/events plus all nine sidecars, original publication/domain receipts, parent Sandbox/Workspace/Worktree state, commands, worker/lifecycle/checkpoint state, accepted recovery work and the associated durable ledger authority. Preserving only immutable event payloads is insufficient: restored heads, evidence generations, audit progress, admission slots, carrier result witnesses and receipts must describe the same point in time. Original runtime/home storage and its ledger identity require their own matching protected recovery evidence; a database-only restore does not recreate a live attachment or persistent home.

Before any live activation, the release owner records protected backup identity/time, exact candidate source and image, reader/recovery floor, schema manifest/checksum, retained key/home references, restore owner and a disposable rehearsal. Include accepted work from every recovery phase and later Agent revisions; prove no input replay, no duplicate publication and exact completion reconciliation. Handle post-backup accepted writes explicitly; never restore an older head over newer acknowledgements. A restored completed carrier still needs the resumable fenced attachment-activation behavior from P1-3.

Closing new writer/recovery admission preserves compatible readers, fitting append capability, exact unknown-outcome reconciliation and accepted-work continuation. It is not permission to restore an old binary that rejects version-2 envelopes or sidecars. TTL, deletion, history truncation, seal replacement, synthetic receipts or relabeling old carrier versions remain prohibited.

Source evidence for P1-2 requires all of: runtime inventory success/missing-grant/foreign-access tests; canonical migration with exact format-2 validator and three nonunique seek indexes; legacy unique-index drift refusal; real isolated-role read/insert/update under that schema; four-phase actual codec fixtures and missing-witness/v1 refusal; bounded discovery explain plans; immutable checksum coverage; and the coherent restore rehearsal. The inventory patch alone does not close P1-2.
