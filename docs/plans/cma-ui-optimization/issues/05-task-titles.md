# 05：按真实任务自动命名并保留手动名称

**What to build:** 第一条真实任务开始后，列表、顶栏和刷新后的 Agent 使用可读任务名；用户改名始终优先。

**Blocked by:** None（可使用现有 Agent 消息入口独立验证）。

**Status:** ready-for-agent

**优先级:** P0

## Acceptance criteria

- [ ] 保留既有优先级：owner 手动名称优先，其次有效 provider title/真实任务预览，再次安全回退；未执行任务的 setup preview 不成为任务标题。
- [ ] 首条真实任务的标题及来源可通过已授权读取恢复，列表、当前页、浏览器标题一致；不靠当前页内存或扫描全部历史维持命名。
- [ ] provider 名称缺失或生成失败时使用有限长度任务摘要；不额外阻塞首条任务，也不为等待命名再发一轮用户对话。
- [ ] 手动改名与晚到 provider 更新并发时保留 owner 名称；刷新与切换 Agent 不闪回旧名称。
- [ ] 自动准备、空文本、很长标题、未知来源和重新连接有稳定回退；正文与 composer 不因名称更新重挂载。
- [ ] 已存在的来源/手动名称字段足够时直接复用；确需补齐持久化投影时兼容旧记录，不默认新增一套标题服务。

## Testing boundaries（2026-11-03 已确认）

- **U/A：** 从现有任务发送/改名入口观察列表和顶栏，刷新后公开读取同一名称；验证手动覆盖和晚到事件隔离。不能证明 provider 一定会生成好标题。
- **R：** 固定 provider 版本实际观测到名称或走真实 fallback，记录来源；命名质量是人工样本审查，不用实现同构的断言评分。
- **首个 red → green：** 用户改名为“工具选型”后到达旧 provider 名称，列表与重开页面仍显示“工具选型”。

## 范围与依赖说明

现有发消息链路足以触发命名，所以不依赖 03；也不依赖 01 的视觉重排。共享区域需协调合并。
