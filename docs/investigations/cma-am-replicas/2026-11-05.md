# Agent Manager replica safety audit — 5 November 2026

Issue: https://github.com/ChronoAIProject/cma/issues/1356. Related to #1343.
Owner: `cma-am-replicas`; branch: `tl/cma-am-replicas/integration`.
Audited source: `934f68607fb60e69a210a8fe5c77cb3219208b9d` (includes #1353/#1355).
All source references below refer to that commit, not a moving branch.

**Verdict: do not scale the current Agent Manager to two serving replicas.**
The store has extensive distributed concurrency controls, but Agent transport
ownership, command execution and live fragment delivery are process-local.
Resolving that boundary requires an architectural prerequisite. This invokes
the task's explicit instruction to stop before implementing a large/risky change.
No application, manifest or production configuration was changed by this audit.
This is a source audit and read-only infrastructure observation, not an executed
two-process correctness proof or a deployment approval.

   ([api/crates/layer2-core/src/sandbox/conversation_live.rs:73](https://github.com/ChronoAIProject/cma/blob/934f68607fb60e69a210a8fe5c77cb3219208b9d/api/crates/layer2-core/src/sandbox/conversation_live.rs#L73), `:92`). Agent SSE

   Durable catch-up polls Mongo (`:235`), so transcript replay can work across
   replicas while live token/thought delivery does not have equivalent behavior.
   This also needs a routing or shared fan-out design and cross-instance tests.
5. `/ready` proves a fresh bounded store ping, not possession of all Agent
   connections ([api/crates/cma/src/health.rs:58](https://github.com/ChronoAIProject/cma/blob/934f68607fb60e69a210a8fe5c77cb3219208b9d/api/crates/cma/src/health.rs#L58), `:105`). Connection recovery

   A Ready second pod can therefore receive work before it has a local runtime.

Client-IP or cookie affinity cannot establish this boundary: browsers, Gateway
requests and independently scheduled workers are different callers. A lease
around background sweeps alone also leaves commands and SSE on the wrong process.
The initial one-to-two transition must address overlap with older workers that
do not participate in the new ownership protocol.

## Routing, local state and load

- Both live Services `cma-agent-manager` and `cma-api` select all Agent Manager
  Pods, with `sessionAffinity: None`. The Gateway provider uses `cma-api` and
  `/api/v2/responses` plus response/event replay
  ([infra/cmaeg/configmap.yaml:161](https://github.com/ChronoAIProject/cma/blob/934f68607fb60e69a210a8fe5c77cb3219208b9d/infra/cmaeg/configmap.yaml#L161), `:168`). An established TCP/SSE/WebSocket
  connection stays with one pod; a subsequent request/reconnect may select any pod.
- Responses v2 reads durable command receipts and history and polls every 250 ms

For maximum application pool size P and S contacted Mongo servers, conservatively
budget up to N × S × P pooled connections, plus monitoring connections and other
services. Under the diagnostic note's primary-only and three-member assumptions,
P=10 means 20 primary application sockets for two clients / 30 for three clients;
allowing two monitoring sockets per member per client gives approximately **32/48**
connections across the set. Secondary reads and retained pools after failover can
increase that bound toward **72/108** for three fully populated per-server pools.
These are planning bounds, not observed occupancy or an Atlas limit.

maxSurge=1 means at least three clients in a two-replica rolling update. Terminating
pods can continue work through the 735-second grace and may exceed desired+surge;

is neither approved by the diagnostic findings nor justified by server evidence.

headroom. Preserve the existing bounded readiness path and compare checkout/hold
latency, occupancy, command load and server headroom. Two clients cannot solve a
