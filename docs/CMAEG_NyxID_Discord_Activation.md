# NyxID native Discord activation contract

Tracking: [CMA #1340](https://github.com/ChronoAIProject/cma/issues/1340) and
[NyxID #2183](https://github.com/ChronoAIProject/NyxID/issues/2183).

## Required client correction

`routing` is a field of the saved channel definition and the dedicated routing
request. It is **not** a field of `ChannelCreateRequest` or
`ChannelUpdateRequest`. Those two request schemas deny unknown fields. Native
Discord creation initializes default-only routing when discovery is enabled;
the client then authors its desired policy using the routing endpoint.

NyxID's `services/nyxbot_gateway_source.rs::apply_policy` inserts `routing` into
the common policy. `handlers/nyxbot.rs::connect_gateway` and transport
replacement send it unchanged to `POST /channels`, then to the full channel
`PUT`. This is present in the sampled production revision `27d3d37553d2` and
in source revision `55151547b117bf282af9f2bbcdb870af929e31c7`. The create fails
during JSON deserialization, before provider lookup, binding, record reservation,
Discord credential verification or native selection. Removing it only from
create leaves the subsequent full update invalid.

NyxID must separate the desired routing policy from channel request bodies:

1. Keep the existing capability checks, stable canonical UUID v4 `record_id`,
   release/ownership fences, creator bearer and private credential handling.
   Send `POST /v1/channels` **without** `routing`. Retain the returned channel
   handle, callback and current record version. The initial native policy is
   generated by CMAEG and is not proof that the desired NyxID policy is saved.
2. Send `PUT /v1/channels/{channel_id}/routing` with only
   `{ "expected_version": <current-version>, "routing": <desired-policy> }`.
   Use the same creator authorization. Additional `consumers` and `rules` may
   be omitted for this default-only policy. The policy endpoint cannot change
   provider identities, credentials or the existing consumer set.
3. If the full channel PUT is still needed for setup or later source/profile
   edits, omit `routing` there too. Each write uses the version returned by the
   previous write; do not reuse the create version after a successful update.
   Full PUT preserves the stored routing policy.
4. Persist the final version and acknowledge both the intended source and the
   desired saved routing before marking native setup ready or completing the
   transport handoff. Update `nyxbot_chats.rs::gateway_policy_acknowledged` and
   settings/reconciliation callers to compare against the desired policy,
   rather than assuming a full PUT can author routing. Retain the existing
   release/rollback and single-transport ownership rules.
5. An exact retry of the routing PUT can confirm an immediately following
   version with identical routing after a lost response. Any different policy
   or later version returns 409; reconcile through an authorized read rather
   than blindly retrying with a new version. Record which operation failed and
   use only allowlisted diagnostic categories, never raw request/response bodies.

The desired Discord routing object can remain:

```json
{
  "version": 1,
  "default_consumer": {"name": "default", "mentionable": false},
  "default_targets": ["default"],
  "max_targets": 1,
  "reply_label": "never",
  "addressing": {
    "mentions": false,
    "command": false,
    "event_field": false,
    "unknown_target_notice": false
  }
}
```

The native source's `type: "discord"`, canonical positive decimal `bot_id`,
`intents: 37377`, scoped open sender/chat admission and `groups: "all"` are
supported. There is no guild/channel ID field required by this create contract.
Omitting `reply.thread_contract` is supported. Credentials remain in the create
body; never put credentials or the full channel policy in the routing body.
The same common-policy construction also adds routing for native WhatsApp;
NyxID should correct serialization there without changing existing relay flows.

## Gateway diagnostics and validation order

Create and full update retain HTTP 400 and problem code `invalid_request`.
An unknown top-level `routing` now returns the fixed detail documented in the
protocol and logs `reason=routing_requires_policy_endpoint`. Other JSON/schema
failures keep the generic detail and log `reason=channel_schema_mismatch`.
These are fixed categories; neither the serde error nor submitted values or
arbitrary field names are logged or returned. Nested unknown `routing` fields
do not receive the top-level routing advice.

The relevant rejection boundaries, in order, are:

| Boundary | Contract / implementation |
| --- | --- |
| Authentication | Creator permission and owner selection; authentication/authorization failures use 401/403, not this schema rejection. |
| JSON and request schema | `http/management.rs`, `channels/requests.rs`: required fields, enum/type shapes, unknown fields; top-level routing fails here. |
| Request metadata | Idempotency header bounds on create; channel handle format on update; schema version, name, profile, source construction and credential bounds in `channels/definition.rs`. |
| Owner and reservation | `channels/management.rs` and `creation.rs`: profile owner/type, stable canonical v4 UUID for native sources, retained creation identity/fingerprint; full update cannot change provider identity or owner. Version/fingerprint conflicts use 409. |
| Definition and feature gates | Core channel/profile/source/partition/reply validation, secret consistency, native writer gate, routing gate and relevant feature consent in `channels/definition.rs` and `write_gate.rs`. |
| Native Discord | Core `channel/discord.rs`: canonical positive u64 bot ID, allowed intent bits and dependencies, MESSAGE_CONTENT plus guild/direct messages, token bounds and admission validation. `channels/native_discord.rs` requires provider response replay before default routing. |
| Provider / record operations | Unknown registered provider or local provider request validation can map to `invalid_request`; provider refusals and record failures have separate mappings in `http/management_responses.rs`. These boundaries are not reached by the misplaced-field request. |

## Verification

Local HTTP fixtures cover the reported source/intents/admission/routing shape,
rejection before provider or record writes, successful create followed by
policy PUT, exact retry and conflicting retry, full-update refusal and routing
preservation, unchanged native/relay creation, and generic secret-safe failures.
They do not connect to Discord or prove production native intake.

After NyxID deploys the client correction, the production acceptance owner must
retry one authorized test Discord channel and record: create 201, routing PUT
200, final desired-policy acknowledgement and native transport, then one
synthetic DM and one server mention admitted and answered through CMAEG native
intake. Verify native inbound/turn/delivery evidence and no duplicate direct
delivery. `selected`/`pending_discovery` or a successful direct relay reply alone
does not establish acceptance. This investigation made no production writes;
connected-platform verification remains pending.
