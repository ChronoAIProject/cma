# Confirmed native Telegram and Discord media edits

This additive `/v1` contract is limited to one confirmed native attachment in one whole platform message. New references require durable upload receipt storage and explicit `native_media_edit` authority. Historical effects-only references remain ineligible for editing, including after issuance is enabled. Multipart per-message references, Telegram albums and Discord messages with multiple attachments remain separate pending work.

`CMAEG_NATIVE_TELEGRAM_MEDIA_EDITS_ENABLED` and `CMAEG_NATIVE_DISCORD_MEDIA_EDITS_ENABLED` default to false and remain false in the manifest. Deploy compatible readers before enabling issuance. Turning issuance off does not revoke a valid retained reference. Provider acceptance is a separate deployment prerequisite; source and fixture validation alone do not establish connected acceptance.

Use the existing REST `POST /v1/messages/{message_ref}/update` or MCP `updateMessage` with an exclusive `native_media_update` object. Supply `Idempotency-Key` for REST or `idempotency_key` for MCP, using the existing visible-ASCII 1–128-byte bound. This key is required for media updates; existing text/card requests remain compatible without it.

```json
{"native_media_update":{"caption":"","text":"Updated visible Discord text"}}
```

Omitted members preserve their current value; an explicit empty string clears; null is rejected. `caption` is the visible Telegram caption and Discord attachment description (alt text). An explicit Telegram caption is a full plain-caption replacement, including when its text matches the previous caption. `text` is Discord visible message content and is refused for Telegram. Caption is bounded to 1,024 UTF-16 units and 4,096 UTF-8 bytes; Discord content to 2,000 UTF-16 units and 8,000 bytes. Ordinary send-caption validation remains unchanged.

```json
{"native_media_update":{"replacement":{"kind":"file","source":{"type":"base64","data":"AQIDBA=="},"filename":"report.bin","mime_type":"application/octet-stream"}}}
```

Replacement requires the original media kind: image, file, audio or video. The source uses the existing bounded public HTTPS/base64 materializer, with 64 KiB aggregate inline content and 8 MiB aggregate prepared bytes. URLs are fetched with existing address-pinning rules; arbitrary native file locators are not accepted. The patch cannot be combined with ordinary text, blocks, native attachments, templates, reply targets or thread flags. Send/reply and other-platform paths refuse it before platform writes.

Telegram uses `editMessageCaption` or multipart `editMessageMedia`, preserving the exact chat/message/topic; the edit API has no topic destination parameter, so the topic is checked in the returned Message. Discord uses one API v10 PATCH: content-only edits omit attachments, description edits retain the exact attachment ID, and replacement supplies only the new placeholder plus `files[0]` in the final attachment list. Content edits suppress mention parsing on every PATCH.

Each reference binds the original admitted Activity, selected default or named consumer, channel record, owner, provider binding and credential, complete native source and routing, exact destination, original media receipt, revision and fixed expiry of at most 24 hours. Same-bot token rotation is permitted only with fresh bot identity verification; mid-flight token changes refuse before writing. Provider credential, consumer-key, source or routing changes revoke the authority. New Telegram channel-post and anonymous-sender references are not issued by this first increment.

The operation claims its key durably and uses the existing exact-message mutation fence shared with delete/reaction. It freezes the full retained snapshot, prepared file digest and intended content. Before dispatch, a CAS changes the current revision from Ready to Attempting, identifying this exact operation, revision and baseline digest; a final custody check follows slow reads and encoding. A definite rejection restores Ready only from that operation's unchanged Attempting state by CAS. A conflict, retirement or changed baseline cannot be overwritten by restoration.

When the response proves the edit and the complete next snapshot is supported, a CAS publishes the next revision and an exact next sealed reference. Use that reference for a new operation. A proved edit whose optional generated metadata cannot support another revision remains confirmed without a next reference; the old authority stays closed in Retired or Attempting. The exact terminal receipt is persisted before the fence can be released. Successful retirement permits fence release; failure to persist the final state keeps it held even when the saved receipt is confirmed. Replay returns that exact receipt, including reference absence, without refetching a source URL.

Timeouts, malformed success bodies, wrong response identities, unexpected changes to untouched owned fields and failed terminal receipt persistence remain unknown and keep the destination fence. Changing a key, consumer, token or process cannot make an uncertain write safe to retry. No automatic reconciliation or resend is provided.

`capabilities.native_media_edits` advertises eligibility for new single-upload references. Per-reference `readMessageCapabilities` returns optional `media_edit` only for a valid current Ready revision; Attempting and Retired states omit it. Neither field changes legacy `edit` semantics or grants delete/reaction permission.

Telegram provides no generic Bot API message-read endpoint. Discord performs an exact message/channel pre-read. Neither reviewed edit API offers a conditional revision or If-Match contract; local fences coordinate CMA replicas, not independent applications using the same credentials. Telegram's incoming edited-message observer is not a complete observer of outbound bot edits; unobserved changes by another application sharing the bot cannot be detected reliably. Provider metadata and transformed media are not a server byte-digest proof. The official contracts are [Telegram Bot API](https://core.telegram.org/bots/api#editmessagemedia) and [Discord Edit Message](https://docs.discord.com/developers/resources/message#edit-message).

Telegram retains the automatic entity kinds `mention`, `hashtag`, `cashtag`, `bot_command`, `url`, `email` and `phone_number`. Spans must be positive, unique, non-overlapping UTF-16 ranges on character boundaries; surrogate splitting and unknown entity fields are refused. A media-only replacement sends the retained caption and entities, caption-above placement and photo/video spoiler state. Explicit caption replacement sends an empty entity list without parse mode; validated newly detected automatic entities in the response may seed the next revision. Caption-only editing preserves stable asset identity and media presentation. Manual formatting, authored text links, user-bound mentions and custom emoji entities remain outside this contract.

Discord retains supported generated link/article/image/video/gifv previews and the ordinary `SUPPRESS_EMBEDS` and `SUPPRESS_NOTIFICATIONS` message flags. It never copies received previews into writable rich embeds or sends a message-flags mutation. Caption/alt edits send the retained attachment ID, description and explicit original `is_spoiler`, omitting filename. Replacements send one new file placeholder and preserve that same spoiler policy. A legacy `SPOILER_` filename requires the documented attachment `IS_SPOILER` flag; the prefix alone does not establish editable authority. Replacement cannot introduce the prefix on a retained non-spoiler message. Attachment `IS_ANIMATED` is retained for unchanged media and may change with a new asset.

The Discord pre-read compares the supported semantic snapshot: text, alt text, message type/reply context, stable file metadata, generated preview semantics and supported flags. It ignores access locators, proxy URLs, and only the documented `ex`, `is` and `hm` signature parameters on official HTTPS attachment CDN URLs. A semantic difference permanently retires the old reference before PATCH; changing the provider state back does not revive it. The API has no atomic conditional write, so a change between pre-read and write remains a platform limitation.

Explicit content or media replacement may legitimately regenerate previews. A supported successful response, including an empty preview list, can seed the next revision. A later preview change retires that revision at the next pre-read; CMAEG does not poll for stabilization or repeat the write. An alt-only edit with changed generated previews can be confirmed without further edit authority when all requested and untouched owned facts are proved. Unsupported authored embeds, components, poll/call modes, ownership changes, missing files or changed omitted text remain ambiguous.

Renewed authority is locally bounded to 128 Telegram entities / 16 KiB presentation, or 10 Discord previews / 32 KiB presentation with bounded fields and nesting. Supported automatic metadata beyond retention limits can preserve a proved edit as confirmed without renewed authority. Invalid or structurally ambiguous metadata cannot prove the effect. These are local retention limits, not provider maximum claims.

Original uploads with supported automatic decorations can receive edit authority. Unsupported optional enrichment or failed optional storage preserves confirmed ordinary delivery and any separately valid effects-only reference; it never resends the upload. Wrong message/destination/bot identity and ambiguous provider writes remain unknown. Exact-reference `media_edit` capability absence is authoritative. Historical immutable records keep their original serialization and digest: new optional presentation fields are omitted when absent, and a later read cannot silently upgrade a legacy plain reference into decorated authority. Compatible readers must precede issuance of the expanded internal snapshots.

Optional pre-send metadata outages omit edit enrichment while ordinary send
checks still apply. A verified custody contradiction refuses the send. Discord's
shared provider cooldown remains authoritative when an optional read observes a
real rate limit; skipping enrichment does not bypass that throttle.

Pending expansion includes individual references for each message in a multipart send, Telegram albums, multiple Discord attachments, stickers, rich-embed authoring and formatting-authoring controls. Decoration support does not grant those capabilities.
