# Native WhatsApp static Forms

Native WhatsApp Forms use official static WhatsApp Flows with Flow JSON 7.3 and Flow message version 3 on Graph v25.0. The existing neutral `Block::Form` is the only authoring input. The gateway compiles and manages the asset, prepares it asynchronously, and sends it only when the agent explicitly commits a Ready preparation. No caller-provided Flow ID, JSON, asset URL, data endpoint, publication mode or token is accepted.

## Consent, gates and activation

The native `whatsapp` source adds optional `forms_enabled`, default false and omitted when false. It is the source owner's consent to create and publish managed static assets with that source's own credentials. New consent and credential replacement verify the app, WABA, phone and granular management/messaging grants. Operator flags `CMAEG_NATIVE_WHATSAPP_FORMS_ENABLED` and `CMAEG_NATIVE_WHATSAPP_FLOW_WRITES_ENABLED` are separate, false by default in checked-in configuration. Authenticated management discovery exposes their optional effective equivalents. Verified eligible private events expose `capabilities.forms`.

Compatible readers and fresh Custom checks precede operator activation for user testing. Native platform acceptance remains explicitly **false** until the user performs the reserved native tests; source validation is not live acceptance. Enabling the operator flags does not grant owner consent. Issuance off preserves retained status, native callback readers and local recovery. Flow-writes off prevents new create/publish boundaries while permitting read-only reconciliation. Withdrawal of owner consent, source credentials, original consumer key/provider or channel generation revokes stale Forms. Unrelated existing WhatsApp controls and group revisions exclude the new consent bit.

## Optional persistent storage

Forms use a dedicated `WhatsappFlow` record kind in `eg_whatsapp_flow_records`, with encrypted CAS rows and no expiry or TTL index. Asset generations, preparation cards and message attempt fences are never placed in the ordinary expiring interaction collection. The existing base schema marker remains version 2 and base runtime/migration role outputs remain unchanged.

Deploy compatible Gateway readers before adding the optional collection/grants. The new executable provides `--print-whatsapp-forms-runtime-role`, `--print-whatsapp-forms-migration-role` and a separate `--migrate-whatsapp-forms`. The optional migration installs the strict record validator, exact ID/owner indexes and a separate `whatsapp_forms` version-1 marker. It refuses unexpected/TTL indexes rather than removing them. Runtime grants have no delete action. Existing Gateway startup does not require these grants or this migration. Forms separately verifies the optional marker, required grants and exact non-TTL indexes within a bounded readiness check; absent/partial migration keeps effective issuance and management workers off. After migration, restart compatible Gateway readers to discover readiness. The legacy remote record transport remains test/migration-only; production readiness requires Gateway-owned Mongo storage.

Source implementation does not run this migration or change production grants. Older isolated readers reject the new collection grant, so remove that optional grant before rolling back to a pre-Forms binary; preserve the collection and all write tombstones. Base readers, channel discovery, owner/retirement logic and existing interaction TTL behavior never scan the new namespace.

## Agent protocol

1. Call `prepareFormReply`: `POST /v1/events/{event_ref}/form-preparation`, with the existing `OutboundMessage` and one required stable `Idempotency-Key`. This operation never sends a customer message.
2. Call `readFormPreparation`: `GET` on the same route. Pending returns `retry_after_ms:1000`. Ready returns an opaque `preparation_ref`. Ready still means `customer_message:not_sent`.
3. Explicitly call the existing `replyToEvent` with the exact original message, a required stable commit `Idempotency-Key`, and `Form-Preparation-Ref`. MCP uses optional `form_preparation_ref` on `replyToEvent`.

Preparation and status each have a real two-second total deadline including fresh channel resolution, authorization and local storage. They make no Meta management calls. Commit retains the ordinary eight-second total budget, compatible with retained ten-second runtime proxies. Duplicate key or selector headers, including identical duplicates, are refused. A timed-out prepare can be reopened with the same key and content. New keys cannot create another content slot or bypass an uncertain send. A form submitted without a selector is refused with `whatsapp_form_preparation_required` before any preparation or send.

The new `FormPreparationReceipt` has `preparation_id`, Unix-second `expires_at`, `customer_message`, and tagged status. Pending, Ready, Declined, Uncertain and Revoked describe managed assets with `customer_message:not_sent`. Uncertain means a create/publish outcome is unproved. Delivery has `customer_message:attempted` and the existing unchanged `IntentReceipt`; Unknown never permits automatic resend or a new key. Existing delivery outcomes and response fields are unchanged. Status after original EventRef expiry returns the existing 410 authorization result.

Preparation/status/commit authorization expires at the original EventRef or service window, whichever is earlier. Issued callback authority has a separate maximum 24-hour card lifetime from preparation, so a successfully sent card is not cut off by the ordinary 30-minute EventRef. Callbacks cannot extend the card lifetime.

## Supported subset and rendering

One form per original event and selected consumer, 1–12 text/number/date/single-choice fields, and optional surrounding plain text. The private message body is at most 1,024 characters, displayed form text at most 4,000, compiled JSON at most 64 KiB and submitted response at most 16 KiB. Preparation also checks the complete encrypted asset and worst-case completion against the 64 KiB record-wire limit before allocating capacity; a large original event or schema can therefore be refused before management work. Text is bounded to 1,000 characters. Numbers use TextInput text mode with a JSON-number pattern to preserve signed, decimal and exponent values. Dates use a single CalendarPicker and canonical ISO date. Choices have 1–20 options and at most one initial selected default. Long labels are retained in TextBody or option descriptions and reported as rendering adaptations. Internal component names are opaque `f0`…; business field and option IDs are restored only after validation.

Media, templates, groups, threads, arbitrary reply targets, independent buttons, multiple forms and other rich-block mixtures are refused. Optional absent/null/empty values are omitted; required omissions, extra/noncanonical field names, duplicate JSON keys, malformed dates/numbers, unknown choices and oversize values are refused. Ordinary provider response delivery cannot fall back to a plaintext form; it must use the preparation protocol.

## Durable mutation and callback boundaries

Managed assets retain encrypted registry generations with unique create/publish attempt nonces before external writes. Lost responses are reconciled read-only. Create reconciliation requires one exact candidate name and downloaded canonical schema; ambiguous candidates remain uncertain. An uncertain publish is never repeated. At most one asset generation per source is active and the registry retains at most 64 generations without deleting write tombstones. Published assets are immutable by gateway policy: current Meta can edit a published asset back to Draft, so commit rechecks exact app/WABA/version/name/schema, validation state and phone health. Asset downloads use a separate credentialless client restricted to public DNS-pinned `scontent.*.fbcdn.net` HTTPS, without redirects or proxy inheritance.

Commit rechecks original authority and remote asset state, persists a unique MessageAttempted nonce, and makes at most one inline customer send within its request deadline. Preparation and management recovery have no customer sender. Caller loss cannot start a later queued send. A provable send first persists the exact ConfirmedUnbound card receipt, then the native receipt and sealed MessageRef. Local recovery finishes those local writes without sending. Unproved remote outcomes remain fenced across keys and restarts. Attempt tombstones are not TTL-deleted.

Completion arrives through the existing HMAC-verified messages webhook as `interactive.type:nfm_reply`, `name:flow`, and JSON-string `response_json`. Meta supplies the original outbound `context.id` and Flow token, not a Flow ID. The context must equal the saved confirmed outbound wamid and the sender/source must equal the original card authority. `context.from` is not phone-resource authority. Tokens are stripped before canonical callback persistence and provider routing. One CAS saves the winning callback and exact EventRef outbox. The typed activity is deterministically reconstructed from that callback and the immutable schema, then checked against the sealed EventRef activity digest; submitted values are stored only once. Exact retries reopen that winner; conflicting facts or another completion cannot replace it. Both consume→route and route→admitted-marker interruptions recover locally, independently of Meta's retry behavior.

## First-increment gaps and evidence

One form per event/consumer, 64 retained generations/source, no registry-reset tooling, the bounded combinations above, and no outside-window approved Flow templates are explicit gaps. They are not a full native-platform-completeness claim. No authenticated Meta mutation or customer send is part of source implementation/testing.

The [evidence manifest](evidence/whatsapp-flows-20261028/manifest.md) records 23 verified successful official sources: eight files pinned to `WhatsApp/WhatsApp-Flows-Tools@4d0a4c30e511913e2126e4f3bc692c79bb05f6bf` and 15 current official documents. Raw SHA-256 values and separate extracted-text hashes were verified on 2026-10-28. Guessed 404 and soft-404 pages are excluded. The old pinned survey uses frozen JSON 3.1; the compiler intentionally emits current publishable JSON 7.3. All evidence retrieval used unauthenticated public GET.
