# Native Lark / Feishu image cards with controls

A native Lark source can send one PNG/JPEG image and buttons or choices in one JSON 2.0 interactive card. `CMAEG_NATIVE_LARK_MEDIA_CONTROLS_ENABLED` defaults to false and the checked-in manifest keeps it disabled. It additionally requires native controls, native outbound media, native intake and durable routed admission. Deploy compatible card readers before enabling issuance. This flag does not change ordinary media or relay delivery.

For a verified original human event with current source and consumer custody, `readEventContext` and `verifyEventContext` expose `capabilities.native_media.controls` with `kinds: ["image"]`, `max_attachments: 1`, `buttons: true`, `choices: true`, `caption_max_chars: 0` and `update: true`. The broader `native_media.kinds` list still describes ordinary media; the nested kinds restrict combinations. Older capability responses omit `controls` or its optional `kinds` property without acquiring new permissions. Clients must not assume that an ordinary file/audio/video capability permits those kinds in an interactive card.

Send one existing `native_attachments` image with regular message text and `buttons` or `choice` blocks. The existing image materializer validates the full source before any native request: up to 64 KiB decoded inline, 8 MiB from pinned public HTTPS, structurally supported PNG/JPEG, matching declared MIME and filename extension. Captions remain unsupported; use message text or text blocks instead. Multiple images require the additional issuance gate described below. Files/audio/video, forms, arbitrary reply targets and invalid bytes are refused. Image replacement requires the separate gate below. The gateway never splits a requested image/control card into separate messages or falls back to a link.

The gateway prepares the ordinary opaque controls record without the raw URL or base64, verifies the exact regional app/bot, and uploads using the native image endpoint. Only a confirmed image key bound to that exact original app, tenant, chat, message, thread and source revision may enter the card. Fresh custody is checked after upload. The compact image key becomes part of the encrypted card's custody digest and is saved before sending. The resulting card contains an `img` element (`img_key`, required plain-text `alt`, `scale_type: fit_horizontal`, `preview: true`) followed by the existing text/opaque controls. The image counts toward the existing 100-element and 28 KiB card limits.

A single confirmed interactive message, its durable native receipt and the existing successful card binding are required before the caller receives a usable message reference. Upload uncertainty, send uncertainty, revoked authority or record failure produces no usable reference and no fallback send. An uploaded resource may remain at the platform after a later failure; no cleanup message or extra external call is attempted. Durable tool replay continues to retain exact confirmed/unknown outcomes through the shared delivery machinery.

`updateMessage` with ordinary text and control blocks preserves the confirmed image without another upload. It uses the existing exact-message fence, superseded old revision, one PATCH, durable confirmed marker and replacement binding. An uncertain PATCH leaves the previous revision fenced. Ordinary text/control updates cannot change the image set, extend its original 24-hour card lifetime or change its consumer. Explicit image replacement follows the separate contract below. Stopping new image-card issuance retains editing, callback consumption and admitted-click recovery for already confirmed cards whose authority remains current. Removing the source or changing app/credentials, actor, consumer/provider or routing prevents stale actions. Historical image-free cards retain exactly their previous serialization and digest.

Local transport tests cover both regional origins, default/named consumers, ordinary/thread replies, buttons/choices, multipart upload then one interactive send, edits, callback replay and recovery, gate-off retained operations, invalid shapes, uncertainty and revocation between upload and send. These are not connected platform acceptance tests; authorized owner testing on Lark and Feishu is still required before claiming live acceptance.

## Two to four images in one control card

`CMAEG_NATIVE_LARK_MULTI_IMAGE_CONTROLS_ENABLED` defaults to `false` and additionally requires the existing image-card, outbound-media and native-control issuance gates. When enabled, verified discovery reports `native_media.controls.max_attachments: 4`; kinds remain `["image"]`, captions remain unsupported and `update: true` continues to mean text/control edits preserving the images. No new public request or SDK type is introduced. With the gate off, new combined requests retain the one-image limit.

The gateway validates every PNG/JPEG source and reserves all image elements and maximum key lengths before making any platform call. The aggregate 8 MiB preparation bound, inline bounds, 100-element limit and 28 KiB card limit remain unchanged. Uploads run in request order with current app/bot and local source/consumer custody checked between writes. Only the complete set of confirmed app-scoped image keys is saved to one durable card, followed by one interactive message containing ordered `img` elements. A failed or uncertain later upload sends no recipient message; previously uploaded resources may remain at the platform. An uncertain card send never triggers splitting, fallback or a blind resend.

Historical text cards still omit all media fields. Historical and newly issued single-image cards retain exactly their scalar `image` representation and existing custody digest. Multiple-image cards use an optional `images` field containing two to four confirmed keys, in order; `image` and `images` are mutually exclusive. Both serving and retained rollback readers must understand `images` **before** new issuance is enabled. Turning the gate off does not make an older reader compatible with retained multiple-image cards.

Text/control revisions preserve every original key in the same order, original destination, consumer, expiry and callback/recovery authority. Without the separate image-replacement gate, updates cannot add, remove, reorder or replace images. Retained operations continue when issuance is disabled, subject to fresh custody. The existing exact-message mutation fence and durable unknown outcomes still prevent repeated uncertain PATCH operations.

Focused local transport tests exercise both regions, two/four images, default/named consumers, ordinary/thread replies, buttons/choices, complete preflight, a rejected or unconfirmed second upload, source/bot revocation between uploads, edits after gate shutdown, callback replay/recovery, retained-order tampering and uncertain-PATCH fencing. These tests do not establish connected Lark/Feishu acceptance.

## Replace the image set on a confirmed native card

`CMAEG_NATIVE_LARK_MEDIA_CARD_REPLACEMENTS_ENABLED` defaults to `false`. When it and native outbound media are enabled, `updateMessage` can replace the complete image set on an existing confirmed image card using the existing `native_attachments` field and complete replacement message text/control blocks. Supply 1–4 validated PNG/JPEG images; count changes such as one to four or four to one are supported. No existing image key is carried forward implicitly when attachments are supplied. Omit attachments to preserve the complete existing set through the normal text/control edit. Empty attachments do not remove images. Forms, non-image attachments, captions, arbitrary destinations and adding images to a previously image-free card remain outside this contract.

Per-event discovery reports `native_media.controls.replace_media: true` only when the replacement gate and existing verified native-media/control discovery requirements hold. The parent's `native_media.max_attachments` bounds replacement sets; `controls.max_attachments` continues to describe **new card issuance** (one image unless its independent multi-image issuance gate is on). Stopping new-card issuance does not revoke replacement of retained image cards while the replacement and outbound-media gates remain enabled. TypeScript and Rust SDKs use their existing message and `replace_media` types; this adds no public request field or persistence schema.

CMA validates the entire replacement set, structural image profiles, declared MIME/extensions and full-card size before the first upload. Every upload rechecks source, app/bot, exact native message and original consumer/provider custody. Upload rejection, unknown upload results, invalid later files or revocation before recipient mutation leave the old persisted card and its callback authority unchanged; uploads are not automatically replayed. Successfully uploaded but unused keys can remain at the provider after a failed operation, but no partial replacement card is sent.

Only after the full ordered set is confirmed does CMA acquire the existing exact-message mutation fence, reread the original card and supersede its revision. It then rechecks fresh native/local custody and sends one full-card PATCH. A confirmed PATCH must be durably recorded before a replacement callback reference is activated. Unknown PATCH or uncertain persistence retains the fence and never retries the PATCH or reuploads through the old reference. The original card record, image keys, destination, owner/consumer and original 24-hour expiry are retained; the new revision never extends that expiry. A one-image revision uses the exact historical scalar `image` shape, and two to four images use the existing ordered `images` shape.

Focused local transport tests cover both regions, default/named consumers, original thread replies, 1→4/4→1/2→3 transitions, scalar compatibility, complete preflight, partial rejected/unknown uploads, unchanged usable old callbacks before mutation, source/consumer revocation, and unknown-PATCH refusal. Connected native account acceptance remains separate and unverified; no production native messages are sent by these tests.

The official full-card update contract and JSON 2.0 image-key contract were fetched on 29 October 2026. Full `content` replacement permits changing the image-element array; neither regional contract imposes the old/new image-count equality restriction. Updates require the same sending identity, a non-recalled shared card with `update_multi: true`, the applicable update scope and a message within 14 days. The provider limits cards to 30 KiB and one message to 5 updates/s; CMA retains its tighter 28 KiB/24-hour bounds and existing pacing. The endpoint has no conditional revision/If-Match contract, so CMA fences its own writers but cannot fence another application using the same bot credentials.
